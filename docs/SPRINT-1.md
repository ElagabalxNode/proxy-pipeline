# Спринт 1: испытания Xray RU → WORLD (вариант 2), затем multi-exit

**Дата старта:** 2026-10-12. **Пересмотр приоритетов:** 2026-10-13.
**Основание:** [plan.md](../plan.md), [инцидент 12.10](../incedent.md), выбор варианта 2: Xray на обоих серверах с независимыми транспортами.
**Цель первого этапа:** воспроизводимо испытать `клиент → VLESS + XHTTP + TLS → RU → VLESS + XHTTP + REALITY → WORLD → интернет`, доказать отсутствие прямого выхода пользовательского трафика из RU и принять решение по результатам измерений. Multi-exit и KZ — следующий этап этого плана, после проверки основной цепочки или документированного отказа от неё.

Это план и журнал разработки, а не отчёт об успешном развёртывании. Реализованные части отмечены ниже; остальные команды и флаги остаются требованиями. Данные об узлах взяты из инцидента; их доступность нужно перепроверить. Для этого испытания данный документ заменяет прежние решения «бриджи заморожены» и «клиентский XHTTP вне спринта», а также приоритет direct из plan.md.

**Выполненные части этапа 2 — RU (2026-10-13):**

- [x] **F4 — проверенная доставка Xray:** опасный inline curl-install удалён. [Установщик](../ansible/roles/bridge_xray_relay/tasks/install.yml) получает официальный ZIP на контроллере либо принимает локальный offline-архив; проверяет SHA256, передаёт по SSH, на RU повторно проверяет checksum, состав и версию исполняемого файла. Поддержаны x86_64/aarch64; RU не обращается к GitHub.
- [x] **F4 — явный pin и защита существующей установки:** обязательны `xray.bridge_release.version` и `archive_sha256`; `archive_path` необязателен. Другой существующий бинарь автоматически не заменяется; существующие geodata/unit сохраняются, неподдерживаемый эффективный ExecStart останавливает роль до смены конфига. Новый unit устанавливается без запуска; выбранной версии для рабочих серверов пока нет.
- [x] **F5 — строгая identity RU:** сохранён приоритет live → backup → fresh. Повреждённый/неполный live-config останавливает роль; если live отсутствует, повреждённый backup также вызывает ошибку. Валидная live identity не зависит от устаревшего backup. UUID, ключи, shortId и размер SS2022-ключа проверяются; неоднозначные/multi-client конфиги не переписываются. Секреты исключены из task/diff output.
- [x] **F4/F5 — совместимость x25519:** принимаются старый `Public key` и новый `Password`; проверяется соответствие сохранённой пары. Нормализация scalar X25519 не меняет сохранённую запись приватного ключа; поведение проверено реальным Xray и соответствует [RFC 7748 §5](https://www.rfc-editor.org/rfc/rfc7748.html#section-5).
- [x] **F5 — транзакция RU:** [apply.yml](../ansible/roles/bridge_xray_relay/tasks/apply.yml) сохраняет прежние config/service/state, валидирует кандидат, проверяет запуск и TCP-listener, затем публикует оба controller state-файла. При обычной ошибке задачи возвращаются прежние файлы и активность/автозапуск сервиса; при первоначальной установке новые config/state удаляются. Даже после успешного отката configure возвращает ошибку. Неизменённый активный конфиг не перезапускается.
- [x] **Регрессии:** тесты точного helper-кода, pin-preflight CLI и настоящих Ansible install/apply tasks во временных каталогах. Systemd в стенде имитируется; рабочие узлы не используются. Проверены offline-доставка, неверные hash/version, запрет замены бинаря/unit, повтор без рестарта, ошибки валидации/запуска и второй записи state, включая откат свежего узла.

**Выполненные части этапа 2 — WORLD (2026-10-13):**

- [x] **F5 — сохранение identity WORLD:** [controller helper](../ansible/roles/exit_xui_reality/files/world_support.py) восстанавливает direct UUID, REALITY key/shortId/SNI/dest, SS2022 password, chain UUID/path из live API. При пустой панели backup из `runtime.json` допустим только для того же `exit_ip`; новый WORLD получает новую identity. Повреждённый runtime, неполный/дублирующийся managed набор и неподдерживаемый layout останавливают применение. Результат новой target-пробы не меняет identity действующего WORLD. Сохранённый chain path передаётся в RU outbound.
- [x] **F1/F5 — обновление по ID:** del-before-add заменён на поддерживаемый API `update/:id`. Неизменённые inbound не записываются повторно; чужие inbound сохраняются. Конфликты портов выявляются до изменений. Повторный configure проверен локально; живое применение ещё требуется.
- [x] **F5 — проверка полного конфига:** до API-записи кандидат, включая чужие inbound/routing, проверяется установленным WORLD Xray. После записи проверяются API read-back, полный сгенерированный конфиг, состояние Xray и принадлежность TCP-listener выбранному бинарю. Неожиданная нормализация панели вызывает откат. Версия/SHA256 бинаря записываются в runtime; это инвентаризация, pin WORLD пока не реализован.
- [x] **F5 — откат и восстановление:** перед изменениями создаётся журнал `.world-transaction.json` с правами 0600; параллельный запуск helper блокируется `.world-configure.lock`. При ошибке API, потере ответа после записи, сбое запуска/публикации state прежние managed inbound восстанавливаются по ID; удаляются только новые inbound этой транзакции. Runtime публикуется атомарно после проверок. При незавершённом откате журнал сохраняется: следующий configure того же WORLD сначала восстанавливает прежнее состояние и завершается с сообщением, после чего configure нужно повторить. Конфликт с внешним изменением не перезаписывается. RU configure и скрипт ротации блокируются при наличии журнала.
- [x] **Часть F6 — configure API через SSH:** cookie/CSRF-сессия хранится в памяти контроллера, запросы идут через туннель к loopback панели. Обычный configure не сбрасывает её credentials/path и не перезапускает `x-ui` при ошибке входа. `validate --deep` на тот момент использовал публичный API; переведён на SSH в блоке F6 ниже.
- [x] **Первичная настройка панели:** добавлен `configure --bootstrap-panel` для новой SQLite-панели. До смены credentials/path helper проверяет отсутствие inbound и сохраняет согласованный SQLite-backup с правами 0600. Непустая/неподдерживаемая БД отклоняется. Скрипт `rotate exit/all` передаёт флаг после создания замены; обычный повторный configure — без него. [Порядок запуска и восстановления](../orchestrator/README.md#world-identity-and-api-recovery).
- [x] **Регрессии WORLD:** ошибки до/после API commit, потеря HTTP-ответа, сбои отката и записи runtime, прерывание контроллера, повреждённые журналы и внешние изменения. Локальная HTTP-панель проверяет cookie/CSRF; настоящая Ansible-задача дважды запускает helper через имитацию SSH-туннеля. Реальный Xray проверяет полный кандидат и владельца listener; секреты не появляются в Ansible `-vv --diff`.

**Выполненные части этапа 2 — firewall WORLD и доступ к API, F6 (2026-10-13):**

- [x] **Раздельные политики chain/direct:** [план правил](../ansible/roles/exit_firewall/files/firewall_plan.py) строится на контроллере до обращения к ufw. Chain-порт — только мост и контроллер. Direct-порты (REALITY; SS2022 по TCP и UDP) — мост, контроллер и выбранная `firewall.direct_policy`: `public`, `allowlist` (`firewall.direct_cidrs`) или `closed`. Значения по умолчанию нет: без выбора configure останавливается до inventory/Ansible, роль также отказывает. Прежний общий allowlist на все порты воспроизводит только явный `closed`.
- [x] **Явный direct-only:** `configure --direct-only` либо `firewall.direct_only: true`. Пустой IP моста без этого режима — ошибка до изменений (ручной RU передаётся через `--bridge-ip`), поэтому забытый флаг не закрывает мосту chain-порт. Режим отклоняется, если мост известен из Terraform, `--bridge-ip` или `state/bridge_runtime.json`, а также с `closed`. `exit_only.yml` больше не падает на роли firewall после настройки WORLD.
- [x] **Панель только через SSH:** порт 3X-UI не открывается никому, включая контроллер. `validate --deep` выполняет `panel_login`/`panel_inbounds` через SSH-туннель к loopback и не обращается к публичному `panel_url`; прокси из окружения для loopback не используется. UI — через `ssh -L`.
- [x] **Административные адреса:** SSH — контроллер (адрес текущей SSH-сессии), `firewall.admin_cidrs` и проверка достижимости с моста; весь мир — только `firewall.ssh_world: true`. Адреса и CIDR проверяются, IPv4/IPv6 поддержаны, `/0` отклоняется.
- [x] **IPv4/IPv6, новый SSH-сеанс, lockout-guard:** [WORLD-хелпер](../ansible/roles/exit_firewall/files/firewall_remote.py) принудительно включает `IPV6=yes` (иначе ufw не управляет ip6tables), после включения проверяет активный default deny и политику DROP цепочки INPUT для IPv4 и, при наличии IPv6 на узле, для IPv6. До изменений снимается снимок файлов правил/настроек ufw и ставится таймер его восстановления; таймер снимается после успешного **нового** SSH-сеанса с контроллера. Прежний guard выполнял `ufw disable`, теперь это запасной вариант при непригодном снимке.
- [x] **Откат правил:** ошибка правила, SSH-проверки или верификации возвращает снимок и завершает play ошибкой. Ручной возврат — `configure --exit-firewall-rollback latest|<снимок>` под тем же guard; повтор восстанавливает тот же снимок. Неизменённое повторное применение снимков не создаёт; хранятся 10 последних.
- [x] **Preflight:** `configure --preflight` проверяет режим chain, pin RU, политику firewall, наличие моста и пароль панели без inventory/Ansible. `rotate-chain.sh` вызывает его после `terraform init` и до plan/apply: прежде отсутствие этих данных проявлялось после замены узла.
- [x] **Регрессии F6:** план правил (политики, отказы, IPv6, дедупликация); настоящая роль через Ansible на эмуляции ufw/iptables/systemd/ssh, различающей файлы правил и загруженный набор — разделение портов, отказ до изменений, повтор без изменений, сбой правила/SSH/IPv6-проверки с возвратом, оставшийся взведённым guard после потери сеанса и его срабатывание, откат; CLI (политика, direct-only, rollback, preflight); deep health через имитацию SSH-туннеля, включая отказ туннеля. Эмуляция выявила и позволила исправить ошибку отката: `latest` указывал на только что снятый снимок.

## Основной выбор: вариант 2 — Xray на обоих серверах

```text
Клиент ── VLESS + XHTTP + TLS ──► RU: Nginx :443, свой домен/сертификат
                                      │ XHTTP через loopback
                                      ▼
                                 RU: Xray, user-in
                                      │ новый VLESS-сеанс, chain UUID
                                      │ XHTTP + REALITY
                                      ▼
                                 WORLD: Xray, chain-in ── freedom ──► Интернет
```

| Участок | Стартовая конфигурация для испытаний |
|---|---|
| Клиент → RU | VLESS + XHTTP + TLS, собственный домен и действительный сертификат; `flow` пустой |
| HTTPS на RU | Nginx на 443; Caddy — допустимая альтернатива. Xray принимает XHTTP только на `127.0.0.1:<local-port>` |
| XHTTP на входе RU | Для первого опыта явно `packet-up`; длинные upload/download проверяются через реальный reverse proxy |
| RU → WORLD | VLESS + XHTTP + REALITY, отдельные UUID, ключевая пара/shortId, path; `flow` пустой. Начать с `mode=auto`, записать фактически выбранный режим |
| WORLD → интернет | `freedom`; назначения клиентов разрешаются на WORLD либо клиентским DNS через туннель |
| Запасной профиль | VLESS + RAW + REALITY на отдельном endpoint; допуск только после тех же измерений |

XHTTP допускает HTTP-посредников и разные режимы передачи; REALITY совместим с RAW, XHTTP и gRPC. Это обоснование конфигурации, **не доказательство доступности у операторов РФ**. Для TLS режим `auto` может выбрать потоковую передачу, поэтому в первом опыте за reverse proxy фиксируем `packet-up`; потоковые режимы проверяем отдельно. [XHTTP, Xray-core](https://github.com/XTLS/Xray-core/discussions/4113), [совместимость транспортов](https://xtls.github.io/en/config/transport.html).

На публичных плечах обычный VLESS с `encryption=none` требует TLS/REALITY. Исключение здесь — доверенный loopback Nginx → Xray после завершения TLS. VLESS Encryption в стартовый опыт не входит. Для обычного XHTTP `flow` оставляем пустым с обеих сторон; `xtls-rprx-vision` из RAW-профиля автоматически не переносим. Документация отдельно описывает исключение с VLESS Encryption. [VLESS outbound](https://xtls.github.io/en/config/outbounds/vless.html).

Цена выбора: дополнительные операции шифрования и доверие к RU, который видит назначения проксируемых запросов. HTTPS сайтов остаётся зашифрованным между приложением и сайтом. На WORLD можно оставить Xray под управлением существующей 3X-UI; миграция панели для опыта не нужна.

## Порядок выполнения

1. **Подготовка:** сверить F1/F2 на контроллере, выполнить F3–F6; записать baseline direct, сделать бэкап и подготовить откат.
2. **Допуск RU/WORLD:** D0 + E3, проверить оба плеча. Если RU → WORLD не проходит реальный XHTTP/REALITY-сеанс, испытать другой target/RU или документировать отказ; не переключать пользователей.
3. **Минимальная цепочка на текущем NL:** D1, D4–D6 и E1/E4; multi-exit не является её зависимостью. Сначала WORLD chain inbound, затем RU outbound и HTTPS-вход, затем тестовые ссылки.
4. **Клиентские измерения:** C1–C4, длительные сессии, отказ WORLD и восстановление. После приёмки — ограниченное переключение на новый профиль.
5. **Расширение:** A1–A5, B1–B2, D2, E2; KZ становится основным только по результатам сравнения. D3 нужен при неуспехе основного опыта.

## Блок D. Вариант 2 и бридж-гибкость — первый приоритет

**D0. Входные данные и сетевой допуск**

Зафиксировать RU-IP/провайдера, собственный FQDN и доступ к DNS, способ получения/продления сертификата, WORLD-IP и chain-port, SSH по ключу, версии Xray на обоих серверах и клиентах. Проверить A/AAAA, время узлов, владельца RU:443 и доступность получения сертификата из сети RU. Для начала — Nginx без CDN, HTTP/2 на публичном TLS-входе. Неверный AAAA удалить до испытаний либо обеспечить работающий IPv6.

На VDSina выполнить отдельные пробы: клиент → RU HTTPS из РФ; RU → WORLD на **фактическом chain-port** (существующий 8443 — кандидат, успех TCP 443 его не заменяет); WORLD → target; реальный XHTTP/REALITY-сеанс с передачей данных. Проверка TLS к самому target с RU лишь вспомогательная. Если chain переносится на WORLD:443, заранее разрешить конфликт с действующим direct inbound — не перезаписывать его вслепую.

*Приёмка:* таблица результатов с временем, точкой запуска, IP/портом, SNI/target, версиями и стадией сбоя. Есть измеренный пригодный RU/WORLD либо зафиксирован блокер, исключающий переключение.

**D1. Независимый выбор входного транспорта и chain-режима**

**Статус:** выбор `xhttp|ss` и независимого порта реализован и проверен на этапе 1. `PROXY_PIPELINE_CHAIN_MODE`, `--chain-mode`, `--bridge-port` работают; приоритет chain: явный флаг → env → существующий автовыбор. Невалидное значение — ошибка до изменений. Осталось отдельно задавать новый входной профиль RU, домен и path; предусмотреть `raw` для опыта D3 с отдельным WORLD inbound. До его реализации `raw` явно отклоняется.

*Приёмка:* тесты CLI/configure подтверждают независимость двух плеч, обработку ручного RU и ошибок; старые профили воспроизводимы, эксперимент включается явно.

**D2. Команды `pipelinectl bridge add / disable / enable`**

Добавление ручного бриджа и управление его состоянием без потери identity. Отключение бриджа не должно незаметно включать RU-direct для старого пользовательского профиля. Direct к WORLD — отдельная явно выбранная ссылка.

*Приёмка:* цикл add → disable → enable на стенде сохраняет UUID/path/домен; после смены WORLD клиентская ссылка RU остаётся валидной.

**D3. Альтернативы при провале измерений**

Сначала локализовать сбой. Проверить другой измеренный REALITY target или RU-провайдера; RAW + REALITY испытать отдельно на проблемном плече. Резервный клиентский RAW/REALITY inbound не делит RU:443 с Nginx: нужен отдельный порт/IP и отдельная ссылка. Vision для RAW — отдельный параметр совместимости, без переноса в XHTTP. SS2022 на RU → WORLD — исторический резерв из инцидента, с отдельным результатом и решением о смене архитектуры.

*Приёмка:* есть сравнение с основным вариантом по той же матрице. Автоматического fallback на прямой интернет из RU нет.

**D4. HTTPS и пользовательский XHTTP inbound на RU**

Nginx завершает TLS собственного домена на 443 и передаёт выделенный случайный path в Xray на `127.0.0.1:<local-port>`. У Nginx и Xray пути совпадают; запросы с суффиксами XHTTP не переписываются. Остальные URL обслуживают обычную страницу. Локальный Xray-порт недоступен извне ни по IPv4, ни по IPv6.

Для стартового `packet-up` использовать HTTP/1.1 к loopback, отключить `proxy_cache`, `proxy_buffering` и `proxy_request_buffering`, согласовать `client_max_body_size` с XHTTP POST, выставить и записать таймауты чтения/отправки. Проверить, что тело запроса и ответ передаются постепенно, а не целиком после завершения; отдельно проверить длительные upload/download и простой соединения. [Директивы Nginx](https://nginx.org/en/docs/http/ngx_http_proxy_module.html).

Перед занятием RU:443 сохранить старый конфиг: текущий RAW/REALITY inbound уже использует этот порт. План переключения должен явно останавливать/переносить его и уметь вернуть; выдавать новый XHTTP-профиль только после проверки. Валидация `nginx -t`, `xray run -test`, проверка сертификата и проба продления — до приёмки.

*Приёмка:* браузер видит валидный HTTPS, тестовый клиент проходит весь пользовательский вход, длинные передачи не обрываются из-за буферизации/лимитов; нет конфликта слушателей.

**D5. Отдельная chain identity и fail-closed routing**

**Статус:** routing существующих inbound исправлен и проверен локально на этапе 1. Отдельные параметры REALITY для chain и новый пользовательский inbound реализованы на этапе 3 и проверены локально. Отдельный UUID на каждый мост (с D2), миграция на действующем WORLD и живой отказ WORLD по E4 остаются открытыми.

Расширить существующий `Chain-Bridge-Entry` на WORLD: отдельный chain UUID уже есть; выделить собственные ключевую пару REALITY, shortId, SNI/target и path, использовать их только в RU outbound. Приватный ключ WORLD не нужен RU; клиент получает лишь UUID и TLS-параметры входа RU. Сохранить chain identity отдельно от direct-профилей WORLD и от identity RU, выдавать отдельный UUID каждому мосту. Оба конца XHTTP используют пустой `flow` (на существующем chain это уже так).

В RU routing явно направлять `user-in` и chain-probe в `chain-to-exit` для TCP/UDP. Удалить обход `geoip:private → direct` для пользовательских inbound: частные/служебные назначения при необходимости блокируются, но не выпускаются с RU. Диагностический `probe-direct-in` оставить только на loopback и разрешать `freedom` исключительно его тегу. Не должно быть пользовательских правил direct, балансировщика с direct-резервом или DNS-fallback через RU. Неизвестные inbound — `blackhole`; безопасный default обязателен, поскольку без совпадения правила Xray выбирает первый outbound. [Routing Xray](https://xtls.github.io/en/config/routing.html).

`AsIs` на RU передаёт доменные назначения дальше без DNS-разрешения для routing; это само по себе не гарантирует отсутствие клиентских DNS-утечек — их проверяет E4. WORLD принимает цепочку, разрешает назначения и выпускает разрешённый трафик через `freedom`.

*Приёмка:* тесты конфигурации подтверждают разделение секретов и маршрутов; E4 доказывает, что при недоступности WORLD клиент получает ошибку, а соединение к сайту с RU не возникает.

**D6. State, ссылки и диагностика нового входа**

Расширить `bridge_identity.json`, `bridge_runtime.json`, шаблоны и генератор ссылок: домен, TLS, XHTTP path/mode и отдельные параметры chain. Текущее восстановление identity ищет REALITY privateKey; добавить восстановление TLS/XHTTP UUID/path без генерации нового пользователя при каждом configure. Ссылки XHTTP не должны содержать `flow=xtls-rprx-vision` или chain credentials. Первичный переход RAW → XHTTP требует нового профиля; дальнейшая ротация WORLD не меняет пользовательскую ссылку RU.

Развести проверки HTTPS-входа и chain. Локальный SOCKS `probe-in` обходит Nginx и клиентский inbound, поэтому зелёный `bridge_chain_http` не заменяет внешний E2E-тест. Старый `dest_tls` относится к REALITY-входу RU: для TLS/XHTTP его отключить как обязательный критерий и добавить проверку собственного HTTPS. Прямой TLS-egress RU оставить диагностикой: его сбой не означает автоматически отказ работающей цепочки. Существующий watchdog уже отличает bridge-egress и ограничивает ротации; сохранить это поведение и добавить классификацию отказов HTTPS-входа, чтобы ошибка сертификата RU не запускала ротацию WORLD.

*Приёмка:* тесты ссылок, восстановления identity и watchdog; после повторного configure и смены WORLD ссылка RU сохраняется. `validate --deep` различает вход RU, chain и полезный трафик.

## Блок E. Проверки и решение о переключении

**E1. E2E из фактических профилей**

Реализовать `pipelinectl test --profile direct-vless|direct-ss|bridge-xhttp [--exit <alias>]`; RAW-резерв добавить только при реализации D3. Из экспортированной ссылки собирать клиентский конфиг совместимого Xray, поднимать локальный SOCKS, выполнять HTTP/HTTPS-запрос, измерять задержку и внешний IP. Проверять поле за полем импорт XHTTP в реальные клиенты; неизвестный транспорт/параметр должен приводить к ошибке, а не молчаливой подмене.

Контроллер проверяет воспроизводимость профиля, домашняя и мобильные сети — фактическую доступность из РФ. Добавить эти результаты отдельными строками `client_profile_*` в `validate --deep`, не заменяя их проверкой TCP. `test --profile all` охватывает включённые профили, отключённые показывает как skipped.

*Приёмка:* виден запрос через весь путь клиент → Nginx → RU Xray → WORLD; внешний IPv4 соответствует WORLD, RTT/скорость записаны. DNS/IPv6 и отрицательные сценарии проверяет E4.

**E2. `validate --deep --exit <alias>`**

После A1 — глубокие проверки любого exit реестра без переключения active. Результат `exits --check` согласован с `validate`; явно указаны точка запуска и проверенный профиль.

**E3. REALITY targets с учётом VDSina**

**Статус:** WORLD → target probe и отдельный [пул chain](../config/reality_targets.chain.yaml) реализованы на этапе 1; [пул direct](../config/reality_targets.yaml) сохранён. `storage.yandex.net`, `yastatic.net`, `cdnvideo.ru`, `okcdn.ru`, `userapi.com` — кандидаты, не гарантированно подходящие targets; `vk.com` из срочного workaround не добавлен. Проверяются фактический `dest`, SNI, сертификат, TLS 1.3 и ALPN, фиксируются ошибки. Осталось проверить настоящий RU → WORLD XHTTP/REALITY-сеанс и связать результаты с отдельной chain identity; успешная проба WORLD → target не доказывает пригодность RU → WORLD.

*Приёмка:* выбранный target прошёл именно нужный маршрут; нет тихого fallback к непроверенному SNI. Смена пула для chain не меняет identity действующих direct-клиентов.

**E4. DNS, IPv6, отказ WORLD и длительная работа — обязательный барьер**

1. На время приёмки отключить клиентский split tunneling и автоматический direct fallback. Проверить доменные и IP-назначения, TCP и используемый UDP. Разрешение доменов/DoH/DoT должно идти через WORLD; bootstrap DNS собственного RU-домена описать отдельно.
2. Проверить IPv4 и IPv6: с рабочим IPv6 WORLD клиент видит его выходной адрес; без него IPv6 блокируется в тестовом профиле, а не уходит напрямую в сеть клиента. Проверить DNS запросами с уникальными именами и сетевым наблюдением; география DNS-резолвера сама по себе маршрут не доказывает.
3. Отключить **тестовый chain inbound/порт** WORLD либо соединение к нему с RU, сохранив SSH и действующий direct. Уже открытые и новые пользовательские соединения должны завершиться ошибкой/таймаутом. По логам/захвату трафика на RU и контрольному серверу убедиться, что пользовательские IPv4/IPv6/DNS не вышли напрямую. Проверить частные/служебные IP и неверный UUID/shortId. Диагностический direct-probe на время наблюдения выключить или учитывать отдельно.
4. Вернуть chain и проверить восстановление без смены клиентской ссылки. Повторить configure и ротацию/переключение тестового WORLD: identity RU стабильна, секреты не попадают в журналы/отчёт.
5. На целевых клиентах выполнить сессию ≥30 минут с upload/download, затем ≥2 часов на прошедшем профиле: большие передачи в обе стороны, простой и возобновление, смена Wi-Fi/мобильной сети. Записать обрывы, RTT, скорость и CPU/RAM обоих узлов.

*Приёмка:* отсутствие утечек подтверждено наблюдением, есть результаты каждой стадии и проверенный откат. При провале критерия профиль не становится основным, даже если TCP/TLS зелёные.

Записывать версию приложения/ядра, ОС, оператора, домашний Wi-Fi/мобильную сеть и время. Профили: direct NL VLESS/SS2022, bridge XHTTP/TLS → XHTTP/REALITY; RAW только после D3, KZ после B2. ## Блок A. Гибкий WORLD (multi-exit) — второй этап

**A1. Реестр exit'ов** — `state/exits/<alias>.json` (identity, IP, регион, источник `terraform|manual`, статус), указатель active и единый резолвер для links/health/watchdog. Миграция текущего `runtime.json` → `nl-cherry` с обратной совместимостью и отдельной chain identity.
*Приёмка:* существующие команды работают поверх реестра; тесты миграции и резолвера.

**A2. `pipelinectl exit add --ip <ip> --user <user> [--alias <name>] [--region <region>]`** — ручной exit через inventory override и exit-роль по `--limit`; повторный configure требует F1/F5, политика портов — F6.
*Приёмка:* VPS добавляется одной командой, повтор не меняет identity, `links` выдаёт `Direct-*-<alias>`.

**A3. `pipelinectl exits [--check]`** — alias, IP, источник, регион, возраст identity, последний validate, blocked-пометка и active; text/json. Живые проверки показывают профиль и точку наблюдения.
*Приёмка:* видно, какие exit'ы готовы для direct и какие — для chain.

**A4. `exit use <alias>` / `exit disable <alias>` / `links --exit <alias>`** — переключение active и RU outbound с проверкой нового WORLD до фиксации state; при ошибке сохранить прежний рабочий WORLD. Отдельная выдача direct-ссылок без переключения active. Отключение активного exit без замены — явная ошибка либо согласованный останов, без RU-direct.
*Приёмка:* NL ↔ KZ переключаются одной командой; identity exit'ов и клиентская ссылка RU стабильны.

**A5. Ротация и watchdog** — Cherry rotation обновляет только собственную запись реестра и связанные RU outbound; blocked-история привязана к alias. Ручные exit'ы не затрагиваются.
*Приёмка:* тесты ротации/неуспешного переключения; watchdog различает отказ узла и конкретного плеча и сохраняет fail-closed.

## Блок B. KZ как второй WORLD

**B1. Пробы до выбора основного exit** — по возможности получить тестовый IP/период; проверять SSH, TCP нужных портов, TLS/REALITY, реальный VLESS и RTT как из РФ, так и с RU. IP reputation — дополнительный сигнал; отсутствие blacklist и регион KZ не гарантируют доступность. Результаты сравнить с NL в C1.
*Приёмка:* есть измеренное преимущество либо отрицательный результат гипотезы; покупка/перенос не обосновываются одной географией.

**B2. Подключение через `exit add`** — `pipelinectl exit add --ip <kz-ip> --user root --alias kz-01`, затем `validate --deep --exit kz-01`, `links --exit kz-01 --export --qr` и тест chain с RU. NL остаётся резервом.
*Приёмка:* KZ проходит E1/E4 и клиентскую матрицу; выбор основного основан на результатах, переключение назад проверено.

## Блок F. Предпосылки безопасного испытания

**F1. Повторное создание inbound** — временный del-before-add из `0e5d45a` заменён на этапе 2 обновлением по ID. Локальные тесты подтверждают повтор без API-записей, сохранение identity/чужих inbound и откат при ошибке. Осталась проверка на фактической версии 3X-UI и живой повторный configure.

**F2. Синхронизация через git — выполнено** пятью коммитами выше. Для каждого опыта записывать фактический SHA контроллера; наличие роли в git не означает её применения на сервере.

**F3. SSH оркестратора/RU/WORLD** — сначала проверить новый вход по ключу и резервный путь, затем `PasswordAuthentication no`, проверка эффективных настроек sshd и fail2ban. Сохранить открытый доступ до успешного нового сеанса; не маскировать MaxStartups увеличением лимита.

**F4. Установка Xray при недоступном GitHub** — заменить `bash -c "$(curl ...)"` отдельной загрузкой с `curl --fail`/проверкой статуса и отдельным запуском. Закрепить версии и проверять checksum артефакта; при недоступности источника на RU доставлять проверенный бинарь с контроллера. Отсутствие бинаря, неподходящая версия или сбой unit — ошибка до рендера/переключения. Проверить разбор вывода `xray x25519` на выбранной версии.

*Выполненная часть F4:* RU переведён на pinned artifact delivery через контроллер, offline-режим и проверку установленного бинаря/unit; поддержаны оба формата x25519. WORLD использует установленный бинарь для config-test и записывает его версию/SHA256 в runtime. Позднее добавлены pin WORLD/3X-UI (закреплённая установка в cloud-init, сверка установленного релиза, `world-release --verify`) и команда `inventory`. Остались выбор рабочих версий RU/WORLD по живой инвентаризации и применение/проверка на узлах. Версия CI не назначается в production автоматически.

**F5. Стабильная identity, валидация и откат** — сохранять и переиспользовать UUID/ключи/shortId/path RU и WORLD; повреждённый state не должен тихо создавать новые ключи. Перед опытом сохранить конфиги, БД 3X-UI, state, tfstate и рабочие ссылки с ограниченными правами; проверить восстановление. Валидировать полный кандидат конфигурации закреплённым Xray до изменения действующих inbound. Обновлять только управляемые объекты; при ошибке возвращать рабочий конфиг и state, при успехе записывать state после проверок. Испытать частичное применение, потерю ответа после API-записи и прерывание контроллера.

*Выполненная часть F5:* строгая identity RU/WORLD, откат RU config/service/controller state и WORLD managed API/runtime реализованы и проверены локально; WORLD дополнен журналом восстановления. Границы перечислены в журнале этапа 2. Добавлен инструмент бэкапа с проверкой целостности (`pipelinectl backup`); бэкап контроллера выполнен, узлов — нет. Отрепетированное восстановление из бэкапов и живая приёмка остаются открытыми; F5 целиком не закрыт.

**F6. Firewall с сохранением direct и доступа управления** — разделить политики: новый chain-port доступен RU/controller, действующий direct остаётся доступен тестовым клиентам согласно выбранной политике. Не применять текущий общий allowlist ко всем портам во время миграции. Учесть direct-only: `exit_only.yml` уже включает firewall, а роль отказывает без bridge IP; предусмотреть явный режим без бриджа. Панель — через SSH/локальный доступ; configure переведён на SSH на этапе 2, deep health ещё обращается по публичному HTTP. Административные адреса учесть явно. Проверить IPv4/IPv6, свежий SSH-сеанс и существующий lockout-guard; при rollback восстановить правила вместе с конфигом. Для сертификата RU открыть только нужный выбранному ACME-методу доступ.

*Выполненная часть F6:* политики chain/direct, явный direct-only, панель и deep health через SSH, административные адреса, IPv6-проверка, снимок/откат правил и preflight реализованы и проверены локально; подробности и границы — в журнале этапа 2. Остались живая приёмка на настоящем ufw и доступ для ACME на RU (вместе с D4).

## Переключение и откат

Перед изменениями записать рабочие direct-профили, SHA/версии, владельцев портов, identity и firewall. При испытаниях временно исключить конфликтующие автоматические ротации watchdog; наблюдение и сбор chainlog сохранить. Публикация тестовой ссылки не означает смену основного профиля.

Переключение допускается после D0/D4/D5/D6, E1/E4 и матрицы C1. При неуспехе вернуть сохранённые конфиги Nginx/Xray/3X-UI, state и правила портов, проверить новый SSH-сеанс и прежний direct. Клиент вручную выбирает резервный direct к WORLD; серверный RU-direct остаётся запрещён. После восстановления вернуть обычный режим watchdog. Результат и фактические команды внести в runbook, историю инцидента дополнять только произошедшими событиями.

## Out of scope

- Миграция 3X-UI → Remnawave, WARP-outbound и автоматическое обновление ядер во время измерений.
- CDN, разделение XHTTP upload/download и VLESS Encryption: отдельные опыты после базовой схемы.
- Terraform-модуль KZ/VDSina: сначала ручные узлы и воспроизводимая настройка.
- Обещание работы при любых белых списках операторов: доступность RU-IP/домена и обоих плеч проверяется на конкретных сетях.

## Риски

| Риск | Действие |
|---|---|
| REALITY на VDSina срывается при доступном TCP | D0/E3, другой target/RU или D3; HTTPS-вход не считать исправлением chain |
| RU-IP/домен недоступен клиенту | Проверять из целевых сетей до переключения; другой транспорт сам по себе адресную блокировку не исправляет |
| XHTTP не поддерживается клиентом или reverse proxy буферизует запросы | Явный packet-up, проверка импорта/версий, длинные upload/download |
| DNS/IPv6/direct обходят WORLD | D5 и отрицательные проверки E4 до раздачи основного профиля |
| Configure ротирует identity или firewall закрывает direct/SSH | F5/F6, проверенный бэкап и откат, свежий SSH-сеанс |
| Watchdog принимает известный сбой RU-egress за отказ WORLD | D6: проверки по плечам, ротация только по релевантному сигналу |
| Рост CPU/памяти и задержек на двух Xray | Измерять оба узла в длительных и одновременных передачах, сравнивать с direct |

## Definition of Done

**Первый этап — решение по варианту 2:**

1. Вход RU — собственный HTTPS-домен и loopback XHTTP; WORLD принимает отдельную защищённую цепочку. Роли, state и ссылки воспроизводимы, версии/SHA зафиксированы.
2. Тесты подтверждают отдельные identity, пустой XHTTP flow, повторный configure и сохранение RU-профиля при смене WORLD; требуемые проверки Ansible и тесты оркестратора проходят.
3. E1/E4 и C1 выполнены: весь путь, DNS/IPv6, отказ WORLD без RU-direct, длительные передачи и восстановление проверены. Неуспешные и пропущенные тесты явно отражены.
4. Direct и SSH пережили эксперимент, откат испытан, runbook и CLIENTS.md обновлены по фактам.
5. Есть решение: **принять вариант 2** для перечисленных сетей/клиентов либо **отклонить по измеренному блокеру** и выбрать следующий опыт. Отрицательный результат завершает исследование, но не считается внедрением или зелёной приёмкой; формальная реализация без рабочих измерений также не является успехом.

**Второй этап — расширение:** A1–A5, D2 и E2 реализованы и проверены; KZ подключён при успешных B1/B2, переключение WORLD не меняет профиль RU. Незавершённые пункты переносятся явно, без отметки «весь спринт выполнен» по результатам одного опыта.

## Данные, которые нужны перед живым испытанием

1. Собственный RU-домен, доступ к DNS и способ выпуска/продления сертификата.
2. RU для первой попытки: повторные пробы VDSina или другой доступный узел; WORLD для старта — текущий NL, если проходит D0.
3. Целевые операторы/сети и версии клиентов для C1, время ограниченного испытания и контрольная точка отката.
4. Для второго этапа: KZ-провайдер и режим выдачи ссылок на несколько WORLD (один active для RU, direct per-exit).
