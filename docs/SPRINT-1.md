# Спринт 1: multi-exit (гибкие exit'ы), KZ-exit, диагностика direct-плеча

**Дата старта:** 2026-10-12
**Основание:** `plan.md` (целевая архитектура), `incedent.md` (инцидент 12.10)
**Цель спринта:** оркестратор управляет несколькими exit'ами (добавление ручного exit'а одной командой, список, переключение, ссылки per-exit) по аналогии с тем, как задумано для бриджей; KZ-нода поднята как второй exit; direct-подключения диагностированы по матрице «клиент × сеть × профиль»; бридж-гибкость (with/without) сохранена как база под возврат YC.

**Текущее состояние (baseline):**
- Exit: `88.216.61.95` (NL-Amsterdam, Cherry) — единственный, живёт в terraform + `state/runtime.json`.
- Бридж: ручной VDSina `212.193.15.90` — транспорт жив, TLS-egress резан ТСПУ, chain=ss не применён; **бриджи заморожены** — подбирать RU-ноды с чистым IP сложно, до возврата YC работаем direct.
- Клиенты (важная поправка): ShadowRocket **нормально работал через YC-бридж** (те же vision-ссылки) → клиентская совместимость формата ссылок подтверждена. Буксует именно **direct-плечо РФ→NL**: v2rayN Win — работает; ShadowRocket iOS — VLESS не подключается, SS2022 нестабилен; ShadowRocket macOS — не подключается.
- Рабочая гипотеза по direct: операторская фильтрация прямых зарубежных IP (мобильные сети — «белые списки», plan.md §4.1) + возможная репутация/шейпинг конкретного IP/подсети NL-exit'а.

## Блок A. Гибкий exit (multi-exit) — приоритет спринта

**A1. Модель multi-exit в state**
Сейчас ровно один exit: terraform(Cherry) → `state/runtime.json`, ссылки/validate читают его напрямую. Ввести реестр: `state/exits/<alias>.json` (identity, IP, регион, источник `terraform|manual`, статус) + указатель активного exit'а (`state/active_exit.json` или поле в runtime). Миграция: текущий runtime.json → alias `nl-cherry`. Обратная совместимость: `links.py`, `health.py`, watchdog читают активный exit через единый резолвер.
*Приёмка:* существующие команды (`links`, `validate`, `doctor`, watchdog) работают без изменений поверх реестра; юнит-тесты резолвера и миграции.

**A2. Команда `pipelinectl exit add --ip <ip> --user <user> [--alias <name>] [--region <region>]`**
Ручной exit вне terraform — зеркало механики ручного бриджа: inventory-override, запуск exit-роли (`exit_xui_reality`) по `--limit`, запись в реестр. Требует E1 (идемпотентность) для повторных configure.
*Приёмка:* новый VPS становится раздаваемым exit'ом одной командой; `links` выдаёт `Direct-*-<alias>` профили.

**A3. Команда `pipelinectl exits`**
Список exit'ов: alias, IP, источник, регион, возраст identity, результат последнего validate, blocked-пометка (`state/blocked_exit_ips.log`), флаг active; по `--check` — живой прогон портов/TLS/ipcheck. Формат text/json.
*Приёмка:* одна команда отвечает «какие exit'ы есть и по каким можно раздавать ссылки».

**A4. Команды `pipelinectl exit use <alias>` / `exit disable <alias>`**
Переключение активного exit'а (пересборка ссылок/QR под него), отключение без удаления state. `links --exit <alias>` — ссылки под любой живой exit без переключения.
*Приёмка:* переключение NL↔KZ — одна команда; identity каждого exit'а стабильна между переключениями.

**A5. Интеграция terraform-exit'а с реестром**
`rotate exit` (Cherry) обновляет свою запись в реестре, не затирая ручные exit'ы; `blocked_exit_ips.log` привязывается к alias.
*Приёмка:* после ротации Cherry реестр консистентен, ручные exit'ы нетронуты; тест watchdog'а на ротацию проходит.

## Блок B. KZ-exit

**B1. Аренда и пробы KZ VPS (до настройки)**
Требования: Ubuntu 22.04/24.04; чистый IP (`pipelinectl ipcheck`, MXToolbox); **доступность TCP 443 из РФ с домашнего и мобильных операторов** (ключевой тест — именно он валит NL direct, см. блок C); RTT из РФ (ожидание: лучше NL); TLS-handshake к exit с SNI маскировки из РФ-сетей; IP не в «hosting»-категории MaxMind (желательно). Результаты — таблицей в спринт/runbook.
*Приёмка:* KZ-нода проходит пробы там, где NL буксует (мобильные сети), либо фиксируем несостоятельность гипотезы и меняем подход.

**B2. Подключение через `exit add`**
`pipelinectl exit add --ip <kz-ip> --user root --alias kz-01`, полный configure по exit-роли, `validate --deep`, `links --exit kz-01 --export --qr`. Раздать KZ-ссылки тестовым клиентам (iOS ShadowRocket в первую очередь).
*Приёмка:* ShadowRocket iOS/macOS подключаются к KZ-exit'у там, где NL не заводился; сессия стабильна ≥30 мин; NL остаётся резервным (`exit use` переключает обратно за минуту).

## Блок C. Диагностика direct-плеча (без «лечения клиента»)

**C1. Матрица «клиент × сеть × профиль»**
Зафиксировать фактуру: iOS ShadowRocket — мобильный оператор vs домашний Wi-Fi; macOS — домашняя сеть; Win — та же сеть, что macOS? Для каждой ячейки: VLESS direct NL, SS direct NL, VLESS direct KZ (после B2). Метрики: подключается/нет, RTT, speedtest, обрывы за 30 мин.
*Приёмка:* заполненная матрица в CLIENTS.md; подтверждённый/опровергнутый вердикт «операторские белые списки / шейпинг NL-подсети».

**C2. Нестабильность SS2022 на iOS**
Собрать симптомы (обрывы? медленно? таймауты?), логи ShadowRocket, проверить с KZ-exit'ом (B2) — отделить проблему плеча от проблемы профиля.
*Приёмка:* SS2022 либо стабилен на KZ, либо задокументирован как нерабочий профиль для iOS с указанием альтернативы.

**C3. ShadowRocket macOS**
Диагностика после появления KZ-ссылок: VLESS и SS. Если не заводится ни один — зафиксировать рекомендованные клиенты macOS из plan.md (V2Box/FoXray/Happ) в CLIENTS.md.
*Приёмка:* macOS-клиент подключён (ShadowRocket или документированная альтернатива).

**C4. Актуализация CLIENTS.md**
Матрица из C1 + рекомендации по выбору exit'а (KZ — основной для РФ, NL — резерв), split-tunneling RU-direct из plan.md этап 3.

## Блок D. Бридж-гибкость (база под возврат YC, пониженный приоритет)

**D1. Восстановить `PROXY_PIPELINE_CHAIN_MODE=ss|xhttp` + флаг `--chain-mode`**
Патч из инцидента потерян (в `cli.py` нет; ручной бридж всегда `xhttp`). Переписать + тесты на `_bridge_chain_mode`/`_do_configure`.
*Приёмка:* оба режима собираются по флагу/env; юнит-тесты зелёные.

**D2. Команды `pipelinectl bridge add / disable / enable`**
Штатное добавление ручного бриджа и переключение chain↔direct без потери identity (QR бриджа выживает). До возврата YC — не разворачивать в прод, только код + тесты.
*Приёмка:* цикл add→disable→enable на стенде; direct-режим (текущий прод) не затрагивается.

**D3. (Отложено) Доводка VDSina** — chain=ss + SNI `yastatic.net` (не vk.com — plan.md §3.3). Выполняется только если появится нужда в RU-бридже до восстановления YC.

## Блок E. Проверки

**E1. E2E-тесты профилей: `pipelinectl test --profile direct-vless|direct-ss [--exit <alias>]`**
Из фактической ссылки собирается клиентский конфиг xray/sing-box на контроллере, локальный SOCKS, HTTP-запрос (generate_204) + RTT. Интегрировать в `validate --deep` как `client_profile_*`. Bridge-профили добавить при возврате бриджа (блок D).
*Приёмка:* падение профиля видно отдельной строкой validate; `test --profile all` зелёный на всех активных exit'ах.

**E2. `validate --deep --exit <alias>`** — прогон глубоких проверок по любому exit'у реестра, не только активному.
*Приёмка:* `exits --check` и `validate` консистентно показывают готовность каждого exit'а.

**E3. Актуализация `config/reality_targets.yaml` под пул plan.md §3.3**
`storage.yandex.net / yastatic.net / cdnvideo.ru / okcdn.ru / userapi.com`; убрать запрещённые дефолты (google/youtube/vk/bing).
*Приёмка:* `probe-targets` ходит по актуальному пулу.

## Риски

| Риск | Митигация |
|---|---|
| KZ-exit тоже режется мобильными операторами (зарубежный IP) | Пробы B1 до оплаты; вердикт матрицы C1 может вернуть нас к бриджам — тогда D3/D2 в приоритет |
| Multi-exit рефакторинг ломает watchdog/ротацию | A1 с обратной совместимостью + тесты watchdog (уже есть, расширить на реестр) |
| Репутация KZ-подсетей (спам-листы, «hosting» MaxMind) | ipcheck/MXToolbox до настройки; reroll IP у хостера |
| F1 затягивается | Workaround из инцидента (ручной del через API) задокументировать, не блокировать B2 |

## Definition of Done (спринт)

1. Реестр exit'ов в state; `exit add` / `exits` / `exit use` / `exit disable` работают и покрыты тестами; terraform-exit живёт в реестре рядом с ручными.
2. KZ-exit в проде: зелёный `validate --deep`, свежие ссылки/QR, ShadowRocket iOS подключается; NL — резерв с переключением одной командой.
3. Матрица «клиент × сеть × профиль» заполнена; по каждой платформе задокументирован рабочий способ подключения (CLIENTS.md).
4. `test --profile all` и `exits --check` в CLI; `pytest` оркестратора зелёный.
5. Код бридж-гибкости (D1–D2) написан и покрыт тестами, прод — direct.
6. Изменения закоммичены, документы обновлены, incedent.md дополнен итогом.
