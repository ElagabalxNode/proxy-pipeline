# План разработки: собственный VPN на эталонной связке (VLESS + XHTTP + REALITY) + Remnawave

**Дата:** 12 октября 2026 года
**Основание:** исследование «Обход блокировок Рунета, октябрь 2026», разделы 3–6 (эталонная связка 5.2)
**Целевой результат:** личный VPN на одной зарубежной ноде, устойчивый к волнам детектов ТСПУ: маскировка под легитимный HTTPS, минимум фингерпринтов, централизованное управление через Remnawave.

> **Осознанное ограничение:** прямое подключение к зарубежному VPS **не работает в режиме белых списков** мобильного оператора (IP ноды не покидает сеть оператора, блок на L3 — см. раздел 4.1 исследования). Эталонная связка решает шейпинг/детекты на L7, но не адресную фильтрацию. Это принятое проектное ограничение; варианты выхода за его пределы — в разделе 5 (эволюция).

---

## 1. Архитектура решения

```
 ┌────────┐   VLESS + XHTTP (packet-up) + REALITY, порт 443    ┌─────────────────┐
 │ Клиент │  uTLS chrome, «тихий» SNI, shortId 00, xmux=1  ──► │ Зарубежный VPS  │ ──► Интернет
 │ (Happ/ │ ◄────────────────────────────────────────────────  │ Remnawave + Xray│
 │v2RayTun│        прямое плечо, TLS-маскировка под CDN         │  (эталон 5.2)   │
 └────────┘                                                    └─────────────────┘
```

**Ключевые проектные решения:**

1. **Одна нода, один эталонный inbound** — без транспортного зоопарка. Именно однородность и «тихость» профиля позволили связке пережить все волны детектов 2026 года (17.02 — объёмные пороги, 05.06 — JA3).
2. **Remnawave как слой управления:** панель + node-агент на том же VPS, подписки, статистика, автоматическое пересоздание конфигов. На одиночной ноде Remnawave чуть избыточен, но даёт чистую эволюцию в мультиноду без миграции (см. раздел 5).
3. **WARP-outbound** для «капризных» доменов (Google, стриминги) — решает проблему капч и антифрода на датацентровом IP.
4. **Split tunneling на клиентах:** RU-домены и госсервисы — direct, остальное — proxy. Снимает конфликт с сервисами, режущими зарубежные IP.

## 2. Этапы разработки

### Этап 0. Инфраструктура (0,5 дня)

**Задачи:**
- [ ] Арендовать зарубежный VPS: NL/DE/FI, минимум 1 vCPU / 1 ГБ RAM / Ubuntu 24.04; провайдеры из отчёта: Aeza (Ryzen 9, безлимит, МИР/СБП), 4VPS (от ~80 ₽), ISHosting (7 дней теста), Hostkey (NL/FI)
- [ ] **Проверить IP до настройки:** не в спам-листах (MXToolbox), поиск Google без капчи, подсеть не в «hosting»-категории MaxMind
- [ ] SSH: ключевая аутентификация, отключить парольный вход, fail2ban
- [ ] Firewall (UFW/security group): открыть только 22 (свой IP) и 443
- [ ] Git-репозиторий: `infra/` (docker-compose, конфиги), `docs/` (runbook-и)

**Критерий приёмки:** VPS доступен по ключу; IP чистый; лишних открытых портов нет.

### Этап 1. Ядро: Remnawave + Xray (1 день)

**Задачи:**
- [ ] Установить Remnawave panel + remnawave-node (Docker Compose, официальная документация remnawave.org)
- [ ] Харденинг панели: нестандартный порт и путь (дефолтные массово сканируются), 2FA, доступ к веб-интерфейсу только через SSH-туннель или IP-allowlist
- [ ] Создать Config Profile с эталонным inbound (раздел 3.1): сгенерировать UUID, пару ключей REALITY (`xray x25519`), рандомный path
- [ ] Создать пользователя, проверить выдачу подписки (URL + QR)
- [ ] Автообновление Xray-core: watchtower на образ ноды — критично против будущих волн детектов
- [ ] UFW: закрыть порты панели и БД от внешнего мира (только localhost/VPN)

**Критерий приёмки:** клиент по подписке подключается, трафик виден в статистике панели, панель недоступна извне.

### Этап 2. WARP-outbound и маршрутизация (0,5 дня)

**Задачи:**
- [ ] Поднять WireGuard-клиент Cloudflare WARP на ноде (`wgcf` → профиль → outbound в конфиге Xray)
- [ ] Правила роутинга: `geosite:google`, стриминги, проблемные банковские API → WARP; остальное → direct
- [ ] Проверить: поиск Google без капчи, YouTube/стриминги не ругаются на датацентровый IP

**Критерий приёмки:** капчи Google исчезли; основной трафик идёт напрямую (скорость не просела).

### Этап 3. Клиенты (0,5 дня)

**Задачи:**

| Платформа | Клиент | Проверить |
|---|---|---|
| Android | Happ / v2RayTun / Hiddify / NekoBox | packet-up активен, подписка обновляется |
| iOS | Happ / Streisand / v2RayTun | **Только packet-up** — лимит 50 МБ Network Extension выгружает stream-up |
| Windows | Hiddify / Throne | uTLS chrome в профиле |
| macOS | V2Box / FoXray / Happ | universal-сборка ядра |
| Роутер (опц.) | sing-box TUN + policy routing на OpenWrt | RU-подсети direct |

- [ ] Профиль маршрутизации на клиентах: RU-домены/госсервисы → direct, остальное → proxy
- [ ] Короткая инструкция для семьи/команды: установка → импорт подписки → включение

**Критерий приёмки:** минимум Android + iOS + десктоп работают одновременно по одной подписке.

### Этап 4. Тестирование и диагностика (0,5–1 день)

**Задачи:**
- [ ] Длительная сессия 2+ часа: видео 1080p, звонки, большие загрузки — без обрывов
- [ ] Проверка «тихости» профиля: нет всплесков RST через ~16 КБ (объёмный порог ТСПУ), нет RST после ClientHello (SNI-детект)
- [ ] Диагностическая таблица симптомов (из отчёта 5.4) в `docs/runbook-diagnostics.md`:
  - SYN без SYN-ACK → сгорел IP → смена IP у хостера
  - RST после ~16 КБ → объёмный порог → проверить packet-up / сменить SNI
  - RST после ClientHello → SNI в блок-листе → ротация SNI из списка
  - живёт, но трафик ~0 → JA3/поведение → обновить ядро, проверить uTLS/xmux
- [ ] Speedtest: зафиксировать baseline скорости и RTT
- [ ] Резервное копирование: `pg_dump` БД Remnawave + экспорт конфига ноды (cron → локально)

**Критерий приёмки:** 2-часовая сессия без деградации; baseline зафиксирован; бэкап настроен.

### Этап 5. Эксплуатация (постоянно)

**Задачи:**
- [ ] Мониторинг: uptime-чек ноды (uptime-kuma на самом VPS или внешний), алерт в Telegram
- [ ] Еженедельно: проверка обновлений Xray-core/Remnawave
- [ ] Ежемесячно: ревизия скорости против baseline (деградация = ранний сигнал детекта/шейпинга)
- [ ] Runbook «сгорел IP»: смена IP у хостера (Aeza/4VPS — быстро) → ничего перенастраивать не надо при REALITY (ключи не зависят от IP), только обновить подписку, если адрес захардкожен
- [ ] Runbook «волна детектов»: порядок действий — обновить ядро → ротация SNI (storage.yandex.net → yastatic.net → cdnvideo.ru → okcdn.ru) → ротация path → смена UUID
- [ ] Квартально: ротация ключей REALITY и UUID (штатная гигиена)

## 3. Конфигурации

### 3.1. Эталонный inbound (раздел 5.2 исследования, без изменений)

```json
"inbounds": [{
  "port": 443,
  "protocol": "vless",
  "settings": { "clients": [{ "id": "<uuid>", "flow": "" }], "decryption": "none" },
  "streamSettings": {
    "network": "xhttp",
    "security": "reality",
    "realitySettings": {
      "target": "storage.yandex.net:443",
      "serverNames": ["storage.yandex.net"],
      "privateKey": "<private-key>",
      "shortIds": ["00"]
    },
    "xhttpSettings": { "mode": "packet-up", "path": "/api/v1/updates" }
  },
  "sniffing": { "enabled": true, "destOverride": ["http", "tls"] }
}]
```

Параметры, зафиксированные эталоном: **packet-up** (не stream-up — выживаемость под поведенческим анализом и на iOS), **shortId `00`**, **uTLS chrome** на клиенте, **xmux maxConnections: 1**, sniffing включён. Путь `/api/v1/updates` заменить на свой правдоподобный под выбранный SNI.

### 3.2. Клиентская share-ссылка

```
vless://<uuid>@<server>:443?security=reality&encryption=none&type=xhttp&mode=packet-up
&sni=storage.yandex.net&fp=chrome&pbk=<public-key>&sid=00&path=/<random-path>#main
```

### 3.3. Пул SNI для ротации (проверенный, из исследования 4.3)

`storage.yandex.net` → `yastatic.net` → `cdnvideo.ru` → `okcdn.ru` → `userapi.com`. Не использовать: google.com, youtube.com, vk.com, bing.com (дефолты гайдов — режутся первыми).

## 4. Риски и митигации

| Риск | Вероятность | Митигация |
|---|---|---|
| Волна детектов под конкретный профиль | Средняя | Автообновление ядра; runbook ротации SNI/path/UUID; мониторинг деградации скорости |
| Сгоревший IP ноды (L3-блок) | Средняя | Хостер с быстрой сменой IP; REALITY переживает смену IP без перегенерации ключей |
| Белые списки на мобильной сети — решение не работает | By design | Принятое ограничение; путь эволюции — раздел 5 |
| Компрометация панели через дефолтные пути | Низкая | Харденинг этапа 1: нестандартный порт/путь, 2FA, allowlist |
| Юридический (281-ФЗ) | Низкая | Только личное использование; никакой продажи доступа и публичной рекламы |

## 5. Эволюция (если понадобятся белые списки)

Архитектура сознательно оставляет точки роста, каждая — отдельный короткий проект поверх готового ядра:

1. **+ Транзитный RU VPS («белый» IP) перед нодой** — каскад из раздела 4.2 исследования: iptables DNAT или HAProxy на российском VPS (Timeweb с бесплатным reroll IP / Yandex Cloud), нода остаётся без изменений. Самый надёжный путь, +~200–1000 ₽/мес.
2. **+ Вторая зарубежная нода** в другой юрисдикции (Remnawave уже готов к мультиноде) — диверсификация под бан подсетей хостера.
3. **+ DNS-туннель (SlipNet/DNSTT)** на том же VPS — канал «на чёрный день» там, где открыт UDP:53.
4. ~~Yandex Cloud Functions~~ — исключено решением от 12.10.2026 (риск бана функций со стороны YC, прецедент API Gateway).
